# M-43 preregistration — H3 `handValue` drop A/B

Date: 2026-08-25. Committed before the run.

**Change under test.** Phase H3 settles the programme's open question: does the placement formula's `handValue` term survive ETW-aware play, or is the second settlement's setup grant already counted once play is ETW-aware, making the explicit term a double count? One arm — `hand_zero` = `simulator/placement/arms/h3_hand_zero.json`, the committed default weights with `handValueWeight: 0` (inside the committed `sweep-bounds.json` range, whose minimum on this axis is 0.0) — against reference `base` = `app_formula:placement/default-weights.json` (`handValueWeight: 0.4`). No engine or formula code changes; zeroing the weight removes the term's contribution without touching the rules-level setup grant itself, so this measures the formula term's pricing, not the engine's rules correctness.

**Why this field answers the question.** The programme's caution is that a null and a correct result look alike unless the A/B is set up to tell them apart. The setup: every seat plays the ETW-aware composite (`heuristic-v1-trader-aware-threat-devcards-denial`, trading on), so the downstream play machinery already consumes exact resource counts through belief and ETW. Under that field, a null on zeroing says the explicit placement-time term adds nothing that ETW-aware play does not already realize — subsumption, the drop case. A real loss says the term still carries unique placement-choice signal even under ETW-aware play — the keep case. (Against a non-ETW field this discrimination would not exist; that corner is deliberately not run.)

**Design.** M-40's confirmation-at-power protocol: `evaluate`, standard4, 4 seats, `--domain tuning`, field `pip_diversity`, every seat on `heuristic-v1-trader-aware-threat-devcards-denial` with `--player-trading`, **8000 boards x 2 reps** (64,000 paired units over 8000 clusters; the plan requires >=8000 boards), reference `base`. Single arm by design: one question, one decision arm, no multiplicity.

**Command** (from `simulator/`):

```text
cargo run --release -p unsettled-sim -- evaluate --layout standard4 --seats 4 --domain tuning --field pip_diversity --arm base=app_formula:placement/default-weights.json --arm hand_zero=app_formula:placement/arms/h3_hand_zero.json --reference base --boards 8000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --out runs/m43-h3-handvalue
```

**Decision rule (fixed before the run).** Recommend dropping the term **only** on verdict `equivalent` with the selected interval strictly inside +-1pp at this power; any other outcome — `better`, `worse`, `inconclusive`, or an `equivalent` whose interval touches a threshold edge — keeps the term. The answer is recorded in `programme.md` either way, closing the open question. Record-only in both directions: nothing is adopted anywhere (`src/engine/weights.ts`, `simulator/placement/default-weights.json`, and the Rust param defaults stay byte-identical; a drop recommendation is an input to the user's Phase I decision, not a change). H4's combine takes no winner from this run in any case — the rule can only recommend removing a term, never adds a `better` arm.

**Prediction (recorded before the run).** M-38's magnitude screens on this axis read flat around the default: 0.2 gave -0.18pp (`equivalent`, clustered interval `[-0.35pp, -0.00pp]`, just barely all-negative) and 0.8 gave +0.06pp (`equivalent`). Linear extrapolation to zero suggests roughly -0.35pp; at the ~+-0.34pp half-width expected from 64,000 paired units the interval most likely sits strictly inside +-1pp, so the expected outcome is `equivalent` with containment — a drop recommendation — unless the term's value is nonlinear below 0.2 or the screen's lean was noise masking a larger true loss.

**Threshold and alpha.** +-1pp practical threshold, alpha 0.05, interval selection as in prior M entries (McNemar vs clustered, whichever the harness selects).

**Admissibility.** `uptime` load recorded before and after; zero illegal actions required; one invocation of 128,000 games (~20-25s expected at the observed ~6-7k games/s), well under the 5-minute ceiling; no concurrent test suite or CPU-heavy job.
