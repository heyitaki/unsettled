# M-66 preregistration: the SP6 adoption gate on `gate2`

Date: 2026-09-03. Committed before the run.

**Authorization, and the spend this run makes.** `gate2` is a held-out domain reserved for exactly one SP6 reading, the adoption decision, and this run is that reading. The `## SP6 decisions, 2026-09-02` note in [placement-programme.md](../../../.claude/specs/simulator/placement-programme.md) records the authorization in terms, and the sentence is quoted here rather than paraphrased, because the M-46 precedent requires a named authorization before a held-out domain is spent: "on 2026-09-02, in advance of either run, the user authorized this run to spend `eval2` exactly once on the SP6 confirmation and `gate2` exactly once on the SP6 adoption decision, and no further approval is sought at the point of spending. Each domain is spent whatever its run reads, and after those two runs no further `eval2` or `gate2` command may ever run." **`gate2` is spent by this run whatever it reads**, adopt or reject, and after it no further `gate2` command may ever run, on these parameters or any others. No retry is preregistered and none may be bought: the standing disposition rule's `inconclusive` retry is a screening rule for `tuning2` and does not reach a held-out domain, and Task 15 of [simulator-placement-sp6.md](../completed/simulator-placement-sp6.md) fixes this run as a single invocation whose verdict decides adoption.

**The condition that let this run be preregistered.** M-64 read **`better`** on `eval2`, `+0.934pp` on a clustered interval of `[+0.579pp, +1.290pp]` whose lower edge sits above the `+0.5pp` bar. That was the preregistered condition for confirming the package and running the gate; had it read `worse`, `equivalent` or `inconclusive`, this preregistration would not exist and `gate2` would have been left unspent.

**Change under test.** One arm, the SP6 candidate vector, against the field's own weights. The candidate is `simulator/placement/sp6-candidate-weights.json`, which M-63 recorded as the output of a coordinate pass that was not needed: M-62's re-screen of the four SP6 candidate axes against the draft-aware field left exactly one survivor, `(expansionWeight, 0.1)`, so the candidate is the live `simulator/placement/default-weights.json` with `expansionWeight` moved from 0 to 0.1 and nothing else moved. The three dropped axes keep their shipped values: `expansionDecay` at 0.5, `robberConcentrationWeight` at 0, `diversityWeight` at 1.6. `simulator/crates/engine/src/policy/params_file.rs::the_sp6_candidate_file_records_the_combined_vector` walks every leaf of the shipped vector and pins that the moved set is exactly that one axis at that value, checks the value against `simulator/placement/sweep-bounds.json`, where `expansionWeight` runs 0.0 to 1.2, and pins the file equal to `simulator/placement/arms/sp6_expansion.json`, the arm M-62 actually read, so the vector this gate decides on and the vector every earlier SP6 entry measured cannot drift apart.

**What this run asks, and what it does not.** M-64 asked whether the `tuning2` gain survived a change of seeds. This run asks M-46's question instead: is the gain real enough to ship as a default. The design is M-64's with the domain moved, so what it adds is a second independent seed set, `gate2` sharing no seed and no generated board with `tuning`, `eval`, `gate`, `tuning2` or `eval2`. What it does not add is any control on field-overfit, because the field is the same `app_formula_draft:default-weights@default-weights` here as on both earlier domains, and none on the opponent model: M-61 measured the greedy model inside every hero at 39.4% of intervening picks named exactly against a draft-aware field, so per the `## The reference field is the draft-aware kind, 2026-09-02` note **no verdict here may be described as taken against a correctly specified model**. Field-overfit is this gate's residual risk in M-46's sense and is accepted as priced rather than removed: the adopted default would be a default for this simulator's composite policy against this field.

**The one thing the gate does not measure, stated before the run rather than after.** The arm moves the hero's weights alone against three seats carrying the field's. Adoption ships the value to every seat, so the post-adoption world is one this run does not observe, exactly as M-46's gate did not observe its own. There is a sharper version of that here than there was at M-46, because the field spelling this programme uses names `simulator/placement/default-weights.json` on both its paths: **after adoption the same spelling denotes a different field**, one where all four seats carry `expansionWeight` 0.1, and no post-adoption run reproduces this reading. That is also why the adoption task re-anchors every SP-family arm pin to a pre-adoption snapshot rather than to the live defaults; without it those arms would silently stop being single-parameter perturbations of the field they were measured against, which is the failure `.claude/specs/simulator/contracts.md` "Weights files" spells out.

**Why this is a single-arm run.** One question, one decision arm, no multiplicity, following M-46's gate and M-45's confirmation-at-power protocol before it. The three axes M-62 dropped get no gate arm: `expansionDecay` and `diversityWeight` resolved `equivalent` and `robberConcentrationWeight` was recorded unresolved after `inconclusive` at both powers, and giving any of them an arm here would spend part of a spend-once decision on a question the screening domain already answered. The field switch is not on trial either. It rests on M-59 and M-61 and landed independently of the weight package, so a rejection here leaves the draft-aware kind the reference field and moves only the candidate vector. M-65's `extension6` reading is record-only by the same decision note and cannot block or license adoption; it read `inconclusive` at `+0.717pp` on `[+0.211pp, +1.222pp]` and did not raise the `worse` flag.

**Design.** `evaluate`, `standard4`, 4 seats, **`--domain gate2`**, field `app_formula_draft:placement/default-weights.json@placement/default-weights.json`, every seat on `heuristic-v1-trader-aware-threat-devcards-denial` with `--player-trading`, `--threads 0`, 8000 boards x 2 reps, which is 64,000 paired units over 8,000 clusters, **`--threshold 0.005`**, `--alpha 0.05`, run from `simulator/`. Reference `base` is the field spec itself, so it sits at the symmetric 0.25 corner and its win rate is the drift check. The decision arm `candidate` carries `sp6-candidate-weights.json` on the hero path with the opponent path pinned to the field's own weights, per the draft-aware arm contract in `.claude/specs/simulator/contracts.md`, so the arm moves the hero's formula and nothing about the opponent model. **The power is a user decision, not a choice made at this point**: the `## SP6 decisions, 2026-09-02` note fixes the gate rule as "M-46's at the new bar: 8000 x 2 on `gate2`", and Task 15 of the plan repeats it, so this preregistration records the consequence of that power below rather than revising it.

**Commands.** Build first, from the repo root, so no compile lands inside a timed window:

```text
RUSTFLAGS="-D warnings" cargo build --release --manifest-path simulator/Cargo.toml -p unsettled-sim
```

Then the single invocation, from `simulator/`, with `uptime` recorded immediately before and immediately after:

```text
target/release/unsettled-sim evaluate --layout standard4 --seats 4 --domain gate2 --field app_formula_draft:placement/default-weights.json@placement/default-weights.json --arm base=app_formula_draft:placement/default-weights.json@placement/default-weights.json --arm candidate=app_formula_draft:placement/sp6-candidate-weights.json@placement/default-weights.json --reference base --boards 8000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --threshold 0.005 --alpha 0.05 --out runs/m66-sp6-gate2
```

The two weights files in this run have distinct stems, `default-weights` and `sp6-candidate-weights`, which is what keeps `heuristics.rs::parse_heuristic` from rejecting the pair on a label collision. The invocation is not piped through `tail` or `head` and does not share its command block with the build, a test suite or any other CPU-heavy job.

**Timing, and why no pilot is registered.** This run plays 2 arms x 8000 boards x 2 reps x 4 hero rotations, **128,000 games**, which is M-64's schedule with the domain changed. M-64 measured that schedule directly at 59.525s and 2,150.3 games/s at 18 workers, so this run is expected to take **about 60 seconds**, and the arm mix that sets the throughput is identical: one zero-`expansionWeight` arm, whose `ScoreRows` cache `draft.rs::Lookahead::new` leaves on, and one nonzero arm, whose cache it turns off. That is far under the eight-minute bar, so it runs in the foreground, and it carries no new layout and fewer than 32,000 boards, so the plan's pilot rule does not fire.

**Decision rule (fixed before the run).** Verdict `better`, the whole selected interval above `+0.005`, **adopts the whole package**: Task 17 of the plan executes the adoption exactly as its Context specifies. **Any other outcome rejects it outright**: `worse`, `equivalent`, or `inconclusive`, regardless of point estimate. There is no partial adoption, no adoption of a smaller value, no second `gate2` invocation and no retry under any outcome. On a rejection, Task 17 takes its skip branch, a dated rejection note is appended to `.claude/specs/simulator/placement-programme.md` saying the package is rejected and nothing moved, and every shipped default stays exactly where it is. **`gate2` is spent either way.** The strictness relative to M-64's confirmation rule is deliberate and is M-46's reasoning unchanged: confirmation asked whether the tuning gain survived the seeds, adoption asks whether it is real enough to ship, and an `inconclusive` gate reading against a package whose whole case is a sub-point effect would mean the effect could not be resolved on the one domain held for deciding it.

**What adoption changes.** On `better`, and only on `better`:

- `src/engine/weights.ts::DEFAULT_WEIGHTS` moves `expansionWeight` from 0 to 0.1. That is the only value that moves in either scorer. `expansionDecay` stays 0.5, `robberConcentrationWeight` stays 0, `diversityWeight` stays 1.6.
- `simulator/placement/default-weights.json` and `simulator/fixtures/placement-parity.json` are regenerated through `simulator/tools/generate-placement-parity.ts`, never hand-edited, and the vitest mirror test that pins the two scorers against each other must pass. Re-verifying the regenerated fixture by hand is a post-completion item, per the standing contract.
- The pre-adoption `simulator/placement/default-weights.json` is snapshotted to `simulator/placement/sp6-pre-adoption-weights.json` with a pin test asserting it equals the literal pre-adoption vector, following the `simulator/placement/phase-i-candidate-weights.json` precedent from M-46.
- `SP2_ARMS`, `SP3_ARMS`, `SP4_ARMS`, `SP5_ARMS` and `SP6_ARMS` pin tests are re-anchored to that snapshot with a comment saying they are frozen measurement records of the pre-adoption field, and `the_sp6_candidate_file_records_the_combined_vector` is updated to record adoption. **No arm file's bytes change**, because the moved parameter already exists in every one of them.
- App tests that pin the factor strip, the road mark or a recommendation ordering at the shipped defaults move to the adopted values, never by loosening an assertion.
- `SIM-GAP-34`, the expansion-unpriced gap, is deleted from `.claude/specs/simulator/gaps.md` and the deletion is named in the commit; the "How to read the gap inventory" sentence in `.claude/specs/simulator/programme.md` re-counts the open placement gaps.

- The corpus is captured before the change and recaptured after, and the entry records which corpora moved. Every corpus scored by the app formula is expected to move, which is what makes this the one task in the plan whose corpora are not required to be byte-identical.
- All six validation commands must be green in the adoption commit.

**What adoption does not change.** The field spelling is unchanged: `app_formula_draft:placement/default-weights.json@placement/default-weights.json` stays the programme's reference field and only the vector inside it moves. The app ships weights only, so its sampled opponent model stays exactly as it is, `opponentTopK` 3 and `softmaxTemperature` 1.25, and neither the deterministic lookahead nor the denial credit is ported into it. The M-40 `diversityWeight` prior is **not** adopted: it read `equivalent` against this field in M-62 and stays a recorded prior for a future programme, as it has since M-46 declined it for the same reason. `robberConcentrationWeight` and `expansionDecay` likewise stay where they ship. `SIM-GAP-35`, `SIM-GAP-36`, `SIM-GAP-37` and `SIM-GAP-41` stay open. No committed M entry, preregistration or decision note is edited.

**Power, and the one risk this design carries.** This is the run's chief hazard and it is named here so it cannot be explained away afterwards, in the same terms M-64's preregistration used, because the arithmetic has not improved. The power is 8000 boards x 2 reps, 64,000 paired units, which is what the user's gate rule fixes. M-62's screen and M-64's confirmation both delivered a half-width near `+/-0.355pp` on this exact contrast at this exact power. A `better` verdict at the 0.5 bar needs the interval's lower edge above `+0.5pp`, so it needs a point estimate above about **`+0.855pp`**. The best available estimate of the effect is about `+0.86pp`: M-62's 256,000-unit retry read `+0.845pp` at `+/-0.177pp` and M-64's held-out reading `+0.934pp` at `+/-0.3555pp`, and inverse-variance weighting those two, which are the two non-overlapping readings, since M-62's screen boards are a subset of its retry's, gives about `+0.863pp`. **The decision threshold and the best estimate of the effect coincide to within a hundredth of a point, so this run is a coin flip by construction even if the effect reproduces exactly.** I record now, before the run, that a rejection on `inconclusive` here should be read in the record as a power outcome and not as a null: it would say the effect could not be resolved above half a point on 64,000 units, not that it is absent, and the tightest estimate of its size would remain M-62's `+0.845pp` on 256,000 `tuning2` units. The retry that would resolve it is not available, because `gate2` is spend-once and the decision rule forbids a second invocation. **None of that licenses treating a rejection as anything but a rejection.** The rule is fixed here and Task 17 applies it as written.

**Prediction (recorded before the run).** I predict a point estimate between `+0.47pp` and `+1.25pp`, centred near `+0.86pp`, the interval being the 95% predictive range around the pooled estimate with this run's own sampling error folded in. On the verdict I predict **`better` and `inconclusive` at close to even, marginally favouring `better`**, at roughly 52 to 48, for the arithmetic above: the threshold sits at about `+0.855pp` and the best estimate at about `+0.863pp`. `equivalent` needs the estimate to fall to about `+0.145pp` for the upper edge to come under the bar, which is more than three and a half standard errors below the pooled estimate, so I put it under 1%. `worse` needs the whole interval below `-0.005pp` and is effectively out of reach; it would say the sign itself was seed-specific across two four-seat seed sets and 320,000 non-overlapping paired units, which nothing in the record makes credible. On the slot structure I predict the mild early-to-late slope both four-seat readings found, roughly `+1.2`, `+1.2`, `+0.5`, `+0.6` across slots 0 to 3, with no slot-0 spike of M-54's kind, though I note that M-64's slot profile already failed to reproduce M-62's on three of four slots at a per-slot half-width near `+/-0.7pp`, so I expect to be wrong in detail again and the per-slot table to stay record-only.

**Admissibility.** The release binary is built with `RUSTFLAGS="-D warnings"` before the measurement starts and is confirmed to report `Finished` against a warm fingerprint, which is M-50's lesson. `uptime` is recorded immediately before and immediately after the invocation and both readings enter the M entry. **Zero illegal actions required**, or the run is inadmissible. The invocation must report domain `gate2` at seed `7670297487904999682`, the decimal form of `0x6a72_5eed_2026_0902`; a different domain or seed makes it inadmissible, and a run that names `tuning`, `eval`, `gate`, `tuning2` or `eval2` is inadmissible on its face, the first three and `eval2` being spent and `tuning2` being the screening domain this decision exists to be held out from. `base`'s win rate is checked against the symmetric 0.25 corner, as every four-seat screen since M-51 has checked its reference, and because `base` carries the field spec exactly this is also the drift check: an unintended touch of the shipped path shows there first. **`base` is not required to reproduce M-62's or M-64's reference win rate and must not be compared with either**, because the domain moved and the board schedule with it; this run establishes the first four-seat draft-aware `base` win rate on `gate2` and nothing reproduces it, since no further `gate2` run may ever be made. `simulator/runs/` is gitignored, so no artifact enters the tree and the M entry is the record.

**Threshold and alpha.** `+/-0.5pp` practical threshold, passed as `--threshold 0.005` because the flag takes a fraction, per SP6's standing threshold in `.claude/specs/simulator/contracts.md`. Alpha 0.05. Interval selection is the harness's own rule in `simulator/crates/cli/src/evaluate.rs::try_paired_stats`, the wider of the McNemar and board-clustered intervals.

**Scope, and what the entry may not be cited for.** One contrast, one axis, one layout, one seat count, one policy, one domain, one spend. The arm moves the hero's weights alone against three seats carrying the field's, so nothing here measures a field where every seat carries `expansionWeight` 0.1, which is the field adoption creates. No reading transfers to `extension6` or to 3, 5 and 6 seat games; M-65 is the only observation outside this corner and it is record-only. The arm moves the setup road as well as the settlement, because `draft.rs::setup_road` applies SP3's road rule and falls through to the far-endpoint scoring only at `expansionWeight` 0, so this reading bundles the two effects and does not separate them, exactly as M-62's, M-64's and M-65's did. The reading is taken against the greedy opponent model M-61 measured at 39.4% exact; what keeps that from biasing the contrast is that the arm and the reference carry the same opponent weights file on the same greedy replay. **A `better` verdict here decides adoption and nothing more**: it does not establish the value is optimal, since `expansionWeight` 0.3 read `inconclusive` twice in M-62 and was recorded unresolved rather than beaten, and no finer sweep was run, and it does not license moving any other axis.
