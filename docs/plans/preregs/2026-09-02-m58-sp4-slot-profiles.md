# M-58 preregistration: SP4 slot-scale profiles

Date: 2026-09-02. Committed before the run.

**Change under test.** `slotScales`, added by Task 17 of `docs/plans/simulator-placement-sp3-sp5.md`. The formula scores a candidate the same way whatever the picking seat's position in the snake, though the positions face different problems: at four seats, slot 0 takes the best single vertex on an empty board and then waits six intervening picks for its second, while slot 3 picks fourth and fifth back to back and chooses its pair jointly. The slot index in a four-seat snake is exactly the count of intervening picks between a seat's two settlements divided by two: six for slot 0, four for slot 1, two for slot 2, none for slot 3. The block is a nested object in both `EngineWeights`, seat count to slot to `{ expansion, diversity }`, shipping at 1.0 in every entry, with exact-key validation on both sides. The `diversity` scale multiplies the whole `diversity` component delta and the `expansion` scale multiplies the `expansion` component; `src/engine/valuation.ts::slotScaleOf` resolves the pair on the TypeScript side from an explicit `DraftSlot`, and `simulator/crates/engine/src/placement/app_formula.rs::AppFormulaScorer::slot_scale` resolves it on the Rust side from the seat, which is the slot by `game.rs::setup_order`. Parity class `W15` pins the two against each other through case `slot-scales`. At 1.0 everywhere the block is exactly a no-op, which the byte-identical corpus diff in Task 17 confirmed. This run asks whether a formula weight that is right on average is wrong slot by slot.

**The arms, and why the expansion pair is absent.** Two decision arms, each the live `simulator/placement/default-weights.json` with only the four `diversity` leaves of the four-seat `slotScales` row moved and every other key, including all three of the other seat-count rows and all four `expansion` leaves, byte-identical:

- `div_rise` = `simulator/placement/arms/sp4_div_rise.json`, slots 0 to 3 at 0.5, 0.8, 1.25, 2.0
- `div_fall` = `simulator/placement/arms/sp4_div_fall.json`, the reverse: 2.0, 1.25, 0.8, 0.5

Reference `base` = `app_formula:placement/default-weights.json`, the shipped vector. Every moved value sits inside the committed `sweep-bounds.json` range for its leaf (`min` 0.25, `max` 4.0), and `simulator/crates/engine/src/policy/params_file.rs::the_sp4_arm_files_are_the_committed_slot_profiles` pins each file as the live defaults with only its declared four-seat leaves moved. **The plan's `sp4_exp_rise` and `sp4_exp_fall` arms do not exist and this run does not measure the expansion axis.** They were conditional on SP3's `expansionWeight` reading `better`, and M-54 recorded no survivor: both expansion arms read `inconclusive` at screen power and again on the preregistered retry, so the axis carries no value into this phase and `expansionWeight` stays at its shipped 0. Scaling a term that is exactly 0 by 0.5 or by 2.0 produces the same 0, so an expansion profile would have been a byte-identical copy of the reference wearing a different name. Only four seats are scaled because only four seats are measured anywhere in this plan; the 3, 5 and 6 seat rows exist so the block's contract is complete and stay at 1.0 in both arms.

**Why these profiles, fixed in the plan's Context before Task 17 was implemented.** The multiset of scales is the same in both arms, `{0.5, 0.8, 1.25, 2.0}`, and only the order differs. That mirroring is the design. It gives two readings that a purely global misweighting cannot separate from a genuine slot effect on its own but that the pair can: if the diversity component is simply mis-scaled by the same factor at every slot, then because the hero rotates through all four slots equally the two arms see the same multiset of perturbations and should read alike, and if diversity is genuinely worth more at some slots than others the two arms should separate. Running only the favoured direction would have made every reading compatible with both stories. The magnitudes bracket the shipped scale by a factor of two either way, which is large enough to move argmaxes often at screen power and small enough that no leaf leaves its committed bounds.

**What the scale actually multiplies, which is coarser than `diversityWeight`.** The `diversity` component is not the spread term alone. `valuation.ts::diversityDelta` is `diversityScore(holdings + candidate) - diversityScore(holdings) - duplicateNumberPenalty(...)`, and `diversityScore` is the `diversityWeight`-scaled resource spread **plus** the four recipe-coverage bonuses (`recipeRoadBonus`, `recipeCityBonus`, `recipeSettlementBonus`, `recipeDevCardBonus`). So a slot scale of 2.0 is not `diversityWeight` at 3.2: it also doubles all four recipe bonuses and doubles the duplicate-number penalty at that slot. That matters because those sub-terms do not all want to move the same way. M-38's screen left `recipeCityBonus` leaning down and `recipeRoadBonus` leaning up, and `diversityCap` raised was decisively `worse`, so this instrument moves a bundle whose parts have different tuned optima. The consequence is stated now rather than after the reading: **a `worse` reading on both arms is as consistent with the bundle being the wrong unit of scaling as with the slot hypothesis being false**, and this run cannot separate those two. That limit is accepted because the alternative, one scale per sub-term per slot, is the general conditional-weight framework `placement-programme.md` deliberately refused to build until a second conditioning variable has earned its place.

**Why this A/B is informative, and what a null would mean.** M-54 produced the reading SP4 exists to test. Its expansion term ran `+2.08pp` and `+2.14pp` at slot 0 on the retry against `+0.79`, `+0.59`, `+1.04` and `+0.19`, `-0.09`, `+0.28` at the later slots, so the pooled estimate on both arms was several times smaller than the slot it was actually working at, diluted by the three slots it barely reached. That is the case for a slot-keyed weight, and it is a case this run cannot make on the expansion axis, so it makes it on the one axis with a large, always-active component and a documented history of being mis-set. **The history is the reason a null here would be worth having.** M-39 and M-40 established that the field wants roughly three times the shipped `diversityWeight` of 1.6: 4.8 read `+1.3pp` with interval `[+0.95pp, +1.63pp]`, missing `better` by half a tenth of a point and never adopted. So the shipped diversity setting is known not to be at its pooled optimum, and this run asks whether the thing wrong with it is the slot conditioning rather than the level. A null at declared power says a single number per axis is the right shape for this weight set and SP4's whole premise is unsupported on the axis where the premise had its best chance, which retires the phase on evidence rather than leaving it open. A separation between the arms says the shape is wrong and a slot-keyed block is worth carrying into SP6.

**Why this field.** A formula weight has to be scored against the live formula, so field and reference are both the app-formula spec over `simulator/placement/default-weights.json`, per the plan's protocol and following M-51's second invocation, M-52, M-53, M-54 and M-57. Every seat runs the post-SP1 composite `heuristic-v1-trader-aware-threat-devcards-denial` with player trading; the hero seat differs from the other three in its placement weights alone, so the three rivals score unscaled at every slot and the arm is a hero-only perturbation. That is the right contrast for a record-only reading and it is not a measurement of a field where every seat conditions on its slot.

**What the arm moves inside the simulator.** Both the settlement argmax and the setup road. `placement/mod.rs::choose_app_formula` scores every legal vertex with `score_for_owner`, which applies the seat's scales, and then, at `expansionWeight` 0, chooses the road by scoring each incident edge's far endpoint through the same scaled entry. A per-seat scale on one component does not cancel out of either argmax, because the other five components are unscaled, so the arm can move the road as well as the settlement. Both effects are part of what is being measured and neither is separated out.

**Design.** `evaluate`, `standard4`, 4 seats, `--domain tuning`, 2000 boards x 2 reps, which is 16,000 paired units over 2000 clusters, `--threads 0`, `--threshold 0.01`, `--alpha 0.05`, reference `base`, both arms in one invocation. That is the plan's screen power for an optional term, matching M-38's placement screens, M-49, M-52, M-53, M-54 and M-57.

**Power, and the reading of record.** At this power the pooled rows of M-54 came back with half-widths of `±0.71pp` and `±0.78pp` and M-57's with `±0.35pp`, so a pooled effect at or above 1pp is comfortably resolvable and a few tenths of a point is at the edge. The per-hero-seat rows are much wider: M-54's screen carried per-slot half-widths near `±1.45pp` and M-57's near `±0.70pp`, the difference tracking how many units each term made discordant. **The per-hero-seat table from Task 1 is the reading of record for which slots drive an arm, and the pooled verdict is the verdict.** Those are two different roles and neither substitutes for the other. The pooled estimate decides the arm's disposition because it is the only row with a preregistered threshold and a declared power behind it. The per-slot table is where the arm's mechanism is read, because a profile that helps at two slots and hurts at two pools toward zero by construction, and this design puts scales above and below 1.0 in the same arm deliberately. A per-slot row is record-only, carries no verdict, and at these half-widths cannot on its own establish a slot effect; what it can do is show whether the two arms' slot patterns are mirror images, which is the discriminating comparison this design was built for.

**Command.** Build first, from the repo root, so no compile lands inside a timed window:

```text
RUSTFLAGS="-D warnings" cargo build --release --manifest-path simulator/Cargo.toml -p unsettled-sim
```

Then, from `simulator/`, with `uptime` recorded immediately before and immediately after:

```text
target/release/unsettled-sim evaluate --layout standard4 --seats 4 --domain tuning --field app_formula:placement/default-weights.json --arm base=app_formula:placement/default-weights.json --arm div_rise=app_formula:placement/arms/sp4_div_rise.json --arm div_fall=app_formula:placement/arms/sp4_div_fall.json --reference base --boards 2000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --threshold 0.01 --alpha 0.05 --out runs/m58-sp4-slot-profiles
```

If and only if an arm reads `inconclusive`, the single preregistered retry is this invocation with `--boards 8000` and `--out runs/m58-sp4-slot-profiles-retry`, `--reps` unchanged at 2, carrying both arms exactly as above so the two are still measured against one reference:

```text
target/release/unsettled-sim evaluate --layout standard4 --seats 4 --domain tuning --field app_formula:placement/default-weights.json --arm base=app_formula:placement/default-weights.json --arm div_rise=app_formula:placement/arms/sp4_div_rise.json --arm div_fall=app_formula:placement/arms/sp4_div_fall.json --reference base --boards 8000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --threshold 0.01 --alpha 0.05 --out runs/m58-sp4-slot-profiles-retry
```

**Decision rule (fixed before the run).** The plan's standing disposition rule, applied per arm without discretion. `better` records that arm as a surviving SP6 candidate. `worse` drops it and the M entry records why the profile was expected to help. `equivalent` at this declared power drops it and records the null as the answer. `inconclusive` buys units exactly once at four times the boards with `--reps` unchanged, in the single retry invocation above, and if the retry is still `inconclusive` the arm is recorded unresolved and the run stops there. **A surviving profile survives as a whole block: all four four-seat `diversity` leaves together, exactly as committed.** No leaf is carried forward on its own and no intermediate profile is constructed after the reading, because both would be choosing the arm from the data; the same reason there is no third profile in either branch, whichever way the two read. If both arms read `better` the better-reading one is the survivor and the other is recorded as the losing direction. Record only in every branch: no shipped default moves, in `src/engine/weights.ts`, `simulator/placement/default-weights.json`, `simulator/placement/phase-i-candidate-weights.json` or anywhere else, the block stays at 1.0 everywhere in every shipped vector, and the two arm files stay the only committed files carrying a non-neutral scale. Nothing is reverted either: a neutral block is a no-op. No entry in `.claude/specs/simulator/gaps.md` moves on this reading in any branch, because SP4 closes no gap of its own, as `placement-programme.md` states in its opening.

**Prediction (recorded before the run).** I predict **`div_rise` reads the better of the two**, with a point estimate between `+0.2pp` and `+1.0pp`, and `div_fall` between `-0.4pp` and `+0.4pp`, both `inconclusive` or `equivalent`, on 5,000 to 9,000 discordant units of 16,000 each. Four things drive that. First, the direction: the diversity component pays for complementing what a seat already holds, and a seat's control over its own complement rises with its slot, from slot 0 whose second pick comes last and takes what six intervening picks left, to slot 3 which chooses both halves of its pair back to back with nothing in between. More weight on complementing where complementing is controllable is `div_rise`. Second, the level: M-40 says the field wants more diversity than it ships with, so an arm that raises the scale anywhere collects some of that global gain at those slots, which pushes both arms up and is why I expect `div_fall` centred at or slightly above zero rather than as `div_rise`'s negative mirror. Third, the discordant count is set high on M-54's explicit lesson, that a term is far more active than its correlation with the other terms suggests: this is not a new input but a factor-of-two move on a large always-active component, so it should reorder argmaxes more often than either expansion arm's 3,143 and 3,697, not less. Fourth, `inconclusive` or `equivalent` rather than `better` because a profile that scales down at two slots is spending half its slots to buy the other half, and nothing in the programme has yet produced a pooled placement effect clearing `+1pp`. Two readings would genuinely change my mind and are named now so they cannot be explained away later. **Both arms negative** would say the bundle is the wrong unit of scaling, that the recipe bonuses and the duplicate-number penalty riding along with the spread term are what the scale is breaking, and the honest conclusion would be that the instrument, not the hypothesis, is what failed. **`div_fall` clearly ahead of `div_rise`** would say the first picker is the one who needs diversity most, because its second pick is nearly forced and its first settlement therefore has to be self-sufficient across resources, which is the opposite mechanism and would make slot 0, not slot 3, the slot SP6 should condition on.

**Threshold and alpha.** `±1pp` practical threshold, alpha 0.05. Interval selection is the harness's own rule in `evaluate.rs::try_paired_stats`, the wider of the McNemar and board-clustered intervals.

**Admissibility.** The release binary is built before the measurement starts and the build is confirmed to report `Finished` against a warm fingerprint, which is M-50's lesson. `uptime` is recorded immediately before and immediately after each `evaluate` invocation and every reading enters the M entry. Zero illegal actions required. No invocation shares its command block with a build, a test suite or any other CPU-heavy job. The screen is 48,000 games, three arms against 2000 boards x 2 reps; the retry, if bought, is 192,000. Throughput should sit near M-57's rather than M-54's, since the scale is one multiplication on a component both scorers already compute and no arm carries a nonzero `expansionWeight`, so no walk runs anywhere in this run. Timing is a throughput observation only; the outcomes are deterministic in the seeds and unaffected by load. Should the extrapolated wall time exceed five minutes the plan's long-run rule applies, though a formula screen at this power has not approached it. The reference arm's win rate is checked against the symmetric 0.25 corner, as M-51 through M-54 and M-57 checked theirs. No reproduction check is registered against any earlier run's numbers: this run's field is the tree at its own commit, whose placement code has moved since M-57 by one block that is a no-op at its shipped values with a byte-identical corpus behind it, and the reference arm carries the shipped vector, so any drift shows up in the reference's own win rate rather than needing a separate assertion. `simulator/runs/` is gitignored, so the artifacts stay out of the tree and the M entry is the record.

**Numbering.** M-57 is the last entry in `.claude/specs/simulator/measurements.md` at this commit, so this run takes M-58. If that file has moved on by the time the run executes, the entry takes the next unused number and this preregistration is cited by filename.
