# M-53 preregistration: SP2b coverage-conditioned port value

Date: 2026-09-01. Committed before the run.

**Change under test.** SP2b added `portCoverageDeficitWeight` to the placement formula, addressing the arithmetic half of `SIM-GAP-37`: `portWeight` is a flat scale, so a port is worth the same to a pair covering five resources as to one covering three, though converting a narrow spread is what a port is for. The term multiplies each per-resource product inside `valuation.ts::portDelta` and its mirror `app_formula.rs::port_delta` by `1 + portCoverageDeficitWeight * deficit_r`, where `deficit_r` is one minus the mean `recipeCap` coverage of the four resources other than the ported one, computed by `valuation.ts::portDeficitFactor` and `app_formula.rs::port_deficit_factor` from the same `coverage` helper the recipe terms use. The post-move deficit prices the post-move half of each difference and the pre-move deficit the pre-move half, so the term stays a true delta and adding a vertex never reprices the holding's existing ports at the new spread. It lands in the existing `port` breakdown component. It ships at 0, where the whole expression collapses to today's arithmetic exactly, so no committed vector's behaviour moved when it landed. This run asks the only question that can move it off 0: does paying a port more when it is the pair's only route to the resources it lacks win more games?

**The arm.** One decision arm, `portdeficit` = `simulator/placement/arms/sp2b_portdeficit.json`, which is the live `simulator/placement/default-weights.json` with `portCoverageDeficitWeight` at 1.0 and every other key byte-identical. Reference `base` = `app_formula:placement/default-weights.json`, the shipped vector. `coverage` returns a value in `[0, 1]`, so `deficit_r` is in `[0, 1]` and at a weight of 1.0 the factor runs over `[1, 2]`: the candidate at most doubles a port's credit for a pair covering nothing else besides the ported resource, and leaves it untouched for a pair already at full coverage across the other four. That is the largest value whose effect is still bounded by "one extra port's worth of credit", which is why it is the screen point rather than a larger one. It sits inside the committed `sweep-bounds.json` range for this axis (`min` 0.0, `max` 4.0). Single arm by design: one question, one contrast, no multiplicity to state.

**Why this A/B is informative, and what a null would mean.** The formula already contains two different opinions about a narrow spread, and this term sets them against each other. `diversityScore` penalises a narrow pair directly, and M-39 and M-40 established that the field wants *more* of that penalty, not less: `diversityWeight` at 4.8 against the shipped 1.6 is worth about `+1.3pp`, interval `[+0.95pp, +1.63pp]`, the strongest surviving prior in the whole H programme. This term pays a narrow pair back, on the argument that a port converts the surplus the narrowness produces. A `better` reading says the port channel is a genuine exception to the diversity penalty and the formula was wrong to price ports flat. A null says the diversity penalty is already the right net opinion about narrow pairs and a port does not buy its way out of one. Either reading is worth having, because `SIM-GAP-37` is otherwise an argument from first principles with no measurement under it.

**Why this field.** A formula weight has to be scored against the live formula, so field and reference are both the app-formula spec over `simulator/placement/default-weights.json`, per the plan's protocol and following M-51's second invocation and M-52. Every seat runs the post-SP1 composite `heuristic-v1-trader-aware-threat-devcards-denial` with player trading, the field whose provenance M-51 established; the hero seat differs from the other three in its placement weights alone. Scoring the arm against a `pip_diversity` field instead would mix a formula-versus-heuristic gap into the contrast, which is what M-38's reference win rate of `0.2331875` against the symmetric 0.25 corner shows happening.

**Design.** `evaluate`, `standard4`, 4 seats, `--domain tuning`, 2000 boards x 2 reps, which is 16,000 paired units over 2000 clusters, `--threads 0`, `--threshold 0.01`, `--alpha 0.05`, reference `base`. That is the plan's screen power for an optional term, matching M-38's placement screens, M-49 and M-52.

**Command.** Build first, from the repo root, so no compile lands inside a timed window:

```text
RUSTFLAGS="-D warnings" cargo build --release --manifest-path simulator/Cargo.toml -p unsettled-sim
```

Then, from `simulator/`, with `uptime` recorded immediately before and immediately after:

```text
target/release/unsettled-sim evaluate --layout standard4 --seats 4 --domain tuning --field app_formula:placement/default-weights.json --arm base=app_formula:placement/default-weights.json --arm portdeficit=app_formula:placement/arms/sp2b_portdeficit.json --reference base --boards 2000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --threshold 0.01 --alpha 0.05 --out runs/m53-sp2b
```

**Decision rule (fixed before the run).** The plan's standing disposition rule, applied without discretion. `better` records 1.0 as a surviving SP6 candidate. `worse` drops the candidate and the M entry records why the term was expected to help. `equivalent` at this declared power drops the candidate and records the null itself as the answer to the narrow-spread question above. `inconclusive` buys units exactly once, at four times the boards (`--boards 8000`, `--reps` unchanged at 2), and if the retry is still `inconclusive` the item is recorded unresolved and the run stops there. Record only in every branch: no shipped default moves, in `src/engine/weights.ts`, `simulator/placement/default-weights.json`, `simulator/placement/phase-i-candidate-weights.json` or anywhere else, and `sp2b_portdeficit.json` is the only committed file carrying a nonzero value on this axis. Nothing here reverts the term either: a weight shipped at 0 is arithmetically inert, removing it is not in SP2's scope, and `SIM-GAP-37` stays open in `gaps.md` in every branch because the gap closes on adoption and adoption is SP6's business.

**Prediction (recorded before the run).** I predict `equivalent` with a negative point estimate, somewhere around `-0.3pp` and inside `-1pp`, on 600 to 1,300 discordant units of 16,000. Three things drive that. First, the direction: M-38 screened `portWeight` in both directions and the field preferred less port credit, `port_lo` at 0.275 reading `+0.51pp` with its interval entirely positive and `port_hi` at 1.1 reading `-1.46pp`, `inconclusive`-worse on 1,349 discordant units. This arm only ever raises port credit, never lowers it, so it pushes along the half of that axis the field already rejected. Second, the magnitude: `port_hi` doubled every port's credit unconditionally, where this arm doubles it only at zero coverage elsewhere and fades to no change at full coverage, so it should land well short of `-1.46pp`; the honest bracket is most of the way between zero and that. Third, the conflict with the diversity prior: M-40 says the field wants narrow pairs penalised harder than the shipped weight penalises them, and this term is a rebate to exactly those pairs. Discordant count should exceed M-52's 707 rather than fall short of it, because `portSurplusThreshold` at 3 keeps the term silent on most pairs but the pairs it does reach are ones where the port term is already the deciding margin. I would be surprised by a positive point estimate, and a `better` reading would be a genuinely informative surprise: it would mean the port channel is an exception the diversity penalty gets wrong.

**Threshold and alpha.** `±1pp` practical threshold, alpha 0.05. Interval selection is the harness's own rule in `evaluate.rs::try_paired_stats`, the wider of the McNemar and board-clustered intervals.

**Admissibility.** The release binary is built before the measurement starts and the build is confirmed to report `Finished` against a warm fingerprint, which is M-50's lesson. `uptime` is recorded immediately before and immediately after the single `evaluate` invocation and both readings enter the M entry. Zero illegal actions required. The invocation shares its command block with no build, no test suite and no other CPU-heavy job. One run of 32,000 games. Expect it to be slower than M-52's 4.40s at 7,265 games/s: the hero seat's weight is nonzero, so its port scoring takes the ten fractional `coverage` powers the zero branch skips on every candidate scan, and that cost falls on one seat in four. Timing is a throughput observation only; the outcomes are deterministic in the seeds and unaffected by load. The reference arm's win rate is checked against the symmetric 0.25 corner, as M-51 and M-52 checked theirs. `simulator/runs/` is gitignored, so the artifact stays out of the tree and the M entry is the record.

**Numbering.** M-52 is the last entry in `.claude/specs/simulator/measurements.md` at this commit, so this run takes M-53. If that file has moved on by the time the run executes, the entry takes the next unused number and this preregistration is cited by filename.
