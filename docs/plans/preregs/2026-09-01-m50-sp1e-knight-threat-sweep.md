# M-50 preregistration — SP1e knight and threat axis sweep

Date: 2026-09-01. Committed before the run.

**Change under test.** Nothing. This is a screen, not a change: five declared `ThreatParams` axes are perturbed one at a time to the endpoints of their committed sweep-bounds ranges and measured against the post-SP1 defaults. No shipped default moves in any branch, and the run's product is a list of axes that survive as SP6 candidates.

**The five axes, and why there are five rather than three.** The programme's SP1e names three: `knightStealWeight`, `knightPlacementWeight`, and SP1d's new `knightReliefWeight`. This run adds `victimNeedWeight` (SP1b) and `needCompletionWeight` (SP1c). The reason is stated plainly because it is a decision this plan made and the programme did not: SP1b and SP1c each minted a brand-new bounds-checked policy parameter at a default nobody measured, and leaving two unswept axes sitting beside three swept ones in the same struct is worse than paying for two more arms in a run that is already paying for eight. The marginal cost is 32,000 games inside one invocation. The two new axes are also the two that actually move the field, so a sweep that skipped them would screen the three axes least likely to read anything.

**Arms (5 axes x 2 arms = 10, plus the reference).** Each arm is a full composite params file under `simulator/placement/arms/sp1e_<slug>_<lo|hi>.json`: the post-SP1 defaults with exactly one leaf moved to that axis's declared bounds endpoint, everything else byte-identical. The committed test `params_file.rs::the_sp1e_arm_files_are_the_committed_bounds_endpoint_perturbations` pins that, in both directions: each of the ten files equals the defaults with its one leaf at its `min` or `max`, and no eleventh `sp1e_*` file exists that a run could pick up unpreregistered.

| Slug | Parameter | Default | lo (bounds `min`) | hi (bounds `max`) |
| --- | --- | ---: | ---: | ---: |
| knsteal | `threat.knightStealWeight` | 12.0 | 3.0 | 48.0 |
| knplace | `threat.knightPlacementWeight` | 30.0 | 7.5 | 120.0 |
| knrelief | `threat.knightReliefWeight` | 12.0 | 3.0 | 48.0 |
| victimneed | `threat.victimNeedWeight` | 0.15 | 0.0375 | 0.6 |
| needcomp | `threat.needCompletionWeight` | 0.35 | 0.0875 | 1.4 |

**Why the endpoints rather than H2's half and double.** The committed range on each of these axes is default/4 to default x 4, so the endpoints are a factor of four either way. H2 screened at half and double and read `equivalent` on both knight axes with single-digit discordance out of 16,000 units (M-41), which is a reading about reach rather than about value: at that perturbation the axis barely changed a decision. Widening to the full declared range is the cheapest way to separate "this axis is flat" from "this axis was not moved far enough to bite", and the declared range is the honest outer limit because a value outside it is one no later phase is allowed to adopt anyway.

**Reference arm.** `base`, the post-SP1 composite defaults, named explicitly through `--arm-policy` even though it equals `--policy`, so the artifact's `armPolicies` map records it alongside the ten perturbations. Every arm, `base` included, places via `pip_diversity` exactly like the field, so an arm differs from the field in the one perturbed policy parameter and in nothing else. `base` is expected to sit near the symmetric 0.25 corner.

**Design.** The plan's screen protocol: `evaluate`, `standard4`, 4 seats, `--domain tuning`, placement field `pip_diversity`, every seat on `heuristic-v1-trader-aware-threat-devcards-denial` with `--player-trading`, `--threads 0`, `--boards 2000 --reps 2`, `--threshold 0.01`, `--alpha 0.05`. That is 16,000 paired units over 2000 clusters per arm.

**One invocation, not several.** The plan allows splitting the sweep if the arm count outruns what a run can carry cleanly. It does not here: 11 arms is half of M-41's 21-arm `h2c` invocation, which carried the whole `ThreatParams` block at this same power without difficulty. Splitting would buy nothing and would cost the shared reference vector that makes the ten estimates directly comparable, since a single run gives all eleven arms the same boards and the same seeds. One invocation is therefore preregistered, and it is the only one.

**Multiplicity, stated rather than corrected.** Ten contrasts at alpha 0.05 against a true null everywhere would be expected to throw roughly one nominal exceedance by chance. No correction is applied, for the same reason M-41 applied none across 128 arms: this is a screen whose output is a candidate list, and every candidate it produces is re-measured at the combined point in SP6, which is where a false positive dies. The M entry records the count of directional readings next to that expectation so a lone `better` is read as what it is.

**Command** (from `simulator/`, `uptime` recorded immediately before and immediately after):

```text
cargo run --release -p unsettled-sim -- evaluate --layout standard4 --seats 4 --domain tuning --field pip_diversity --arm base=pip_diversity --arm knsteal_lo=pip_diversity --arm knsteal_hi=pip_diversity --arm knplace_lo=pip_diversity --arm knplace_hi=pip_diversity --arm knrelief_lo=pip_diversity --arm knrelief_hi=pip_diversity --arm victimneed_lo=pip_diversity --arm victimneed_hi=pip_diversity --arm needcomp_lo=pip_diversity --arm needcomp_hi=pip_diversity --arm-policy base=heuristic-v1-trader-aware-threat-devcards-denial --arm-policy knsteal_lo=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_knsteal_lo.json --arm-policy knsteal_hi=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_knsteal_hi.json --arm-policy knplace_lo=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_knplace_lo.json --arm-policy knplace_hi=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_knplace_hi.json --arm-policy knrelief_lo=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_knrelief_lo.json --arm-policy knrelief_hi=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_knrelief_hi.json --arm-policy victimneed_lo=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_victimneed_lo.json --arm-policy victimneed_hi=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_victimneed_hi.json --arm-policy needcomp_lo=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_needcomp_lo.json --arm-policy needcomp_hi=heuristic-v1-trader-aware-threat-devcards-denial@placement/arms/sp1e_needcomp_hi.json --reference base --boards 2000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --threshold 0.01 --alpha 0.05 --out runs/m50-sp1e
```

**The retry, preregistered now so it cannot be chosen later.** If and only if an axis reads `inconclusive`, that axis's two arms are re-run exactly once at four times the boards, `--boards 8000 --reps 2`, every other argument identical, in a single follow-up invocation carrying `base` and only the inconclusive axes' arms, written to `runs/m50-sp1e-retry`. Boards rise, reps never do: clustered precision comes from the number of boards. An axis still `inconclusive` after the retry is recorded unresolved and the sweep stops there. No axis reading `better`, `worse` or `equivalent` is re-run for any reason.

**Decision rule (fixed before the run).** The plan's standing disposition rule, and nothing else. `better` records the axis and its measured value as a surviving SP6 candidate. `worse` records the direction and drops it. `equivalent` at this declared power drops it and records the null as the answer. `inconclusive` buys the single retry above. Record only, adopt nothing: after this run `src/engine/weights.ts`, `simulator/placement/default-weights.json`, `simulator/placement/policy-default-params.json`, `simulator/placement/phase-i-candidate-params.json`, `HeuristicParams::default()` and every committed arm file are byte-identical to what this preregistration's commit carries. The surviving-axis list, possibly empty, goes in the M entry and is the only thing this run produces.

**Interpretive note, per `contracts.md`.** The default ordering of the threat terms is regime-dependent: it holds above danger roughly 0.108 and 0.105 and reverses below. A single-parameter verdict on this instrument therefore averages over both regimes, and a null does not establish an axis dead in either regime alone. This applies to `victimneed` and `needcomp`, which sit inside that ordering. It does not apply to the three knight axes, which score an action rather than rank the threat terms.

**Prediction (recorded before the run).** The three knight axes should repeat M-41's reading with wider arms: `knsteal` and `knplace` moved 2 to 7 units of 16,000 at half and double, and a factor of four should raise that into the low tens rather than the hundreds, because `knight_action_score` competes against the rest of the turn's actions and the knight is rarely the marginal choice. `knrelief` is unmeasured but rides the same decision, so I predict it behaves like its two siblings. All three should read `equivalent` with intervals narrow enough that the verdict is real rather than a degenerate zero. The two new axes are where movement lives: SP1b's term moved 62 of 400 corpus games on `standard4` and SP1c's moved 37 of 400, both against the term's absence, so at a quarter and four times the default I expect discordance in the hundreds and the widest intervals in the table. I predict every point estimate inside +-0.5pp, no arm reading `better`, and the most likely non-`equivalent` outcome being `inconclusive` on `victimneed_hi` or `needcomp_hi`, the two arms that push a new term hardest. A `better` on either new axis would say SP1 under-weighted the term it just added, which is worth knowing and is exactly what the SP6 candidate list is for.

**Threshold and alpha.** +-1pp practical threshold, alpha 0.05. Interval selection is the harness's own rule, the wider of the McNemar and board-clustered intervals.

**Admissibility.** The release binary is built before the measurement starts, so no compile overlaps a timed run. `uptime` immediately before and immediately after the invocation, both in the M entry. Zero illegal actions required. Nothing else CPU-heavy runs concurrently, and the invocation never shares a command block with a build or a test suite. 176,000 games at the observed ~7k games/s is well under the 5-minute ceiling. `simulator/runs/` is gitignored, so the artifact stays out of the tree and the M entry is the record.

**Numbering.** M-49 is the last entry in `.claude/specs/simulator/measurements.md` at this commit, so this run takes M-50. If that file has moved on by the time the run executes, the entry takes the next unused number and this preregistration is cited by filename.
