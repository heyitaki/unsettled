# M-60 preregistration: SP5 setup denial

Date: 2026-09-02. Committed before the run.

**Change under test.** `setupDenialWeight`, added by Task 23 of `docs/plans/simulator-placement-sp3-sp5.md` and implemented in `simulator/crates/engine/src/placement/draft.rs`. M-59 established that the draft-aware kind is worth `+1.6484pp` over the shipped greedy setup, and everything it prices is the hero's own pair: `Lookahead::value` ranks a candidate by its marginal score plus the best second settlement still legal once the intervening rivals have replayed their argmaxes. What a candidate costs the rivals is visible to that replay and unpriced by it. `replay` already scores each intervening seat's row twice: once with the hero's candidate taken, which is the pick the rival makes, and once with that vertex vacated for legality alone, which is the pick it would have made had the hero left it there. `denial_gain` differences the two and floors at 0, `replay` sums the differences into `Lookahead::denial`, and `value` pays the hero `setupDenialWeight` times that sum on top of the pair value. The loss is scored at the rival's own weights and the price put on it is the hero's, so an arm that sweeps the hero's formula moves one side of the draft and leaves the model it replays the field with alone. `AppFormula` never reads the field, and neither does the app: `src/engine/weights.ts` declares it with a comment saying so, the mirror image of the search-control fields the simulator ignores.

**What the credit is worth in theory, which is what fixes the two arm values.** The value of denying a rival splits in two and the lookahead already holds one half. When the vertex the hero takes would have been a rival's pick, the rival takes something else, and if that something else is a vertex the hero wanted for its second settlement then the loss comes straight back to the hero as a better surviving second site, which `value` already counts through the replay. What the credit adds is the rest: the part of the rival's loss that never reaches the hero's own board. That part is a pure externality at four seats. A loss to one rival redistributes over the other three seats, and if it redistributes evenly the hero collects about a third of it, so the break-even price on the externality is near `1/3` in the formula's own score units, which are comparable across seats because every seat runs the same weights file. **`sp5_denial_lo` at 0.25 sits just under that break-even and `sp5_denial_hi` at 1.0 sits three times over it**, pricing a rival's loss as if it were the hero's own gain, which is the zero-sum error a four-seat game does not support. Both values are inside the committed `sweep-bounds.json` range for the axis, `min` 0.0 and `max` 4.0.

**The arms.** Two decision arms, each the draft kind with the arm file on its hero path and the shipped vector on its opponent path:

- `denial_lo` = `app_formula_draft:placement/arms/sp5_denial_lo.json@placement/default-weights.json`, registered as `app_formula_draft:sp5_denial_lo@default-weights`
- `denial_hi` = `app_formula_draft:placement/arms/sp5_denial_hi.json@placement/default-weights.json`, registered as `app_formula_draft:sp5_denial_hi@default-weights`

Reference `draft` = `app_formula_draft:placement/default-weights.json@placement/default-weights.json`, the same kind carrying the shipped vector on both paths, which is exactly the arm M-59 measured. Each arm file is the live `simulator/placement/default-weights.json` with `setupDenialWeight` alone raised and every other key byte-identical, and `simulator/crates/engine/src/policy/params_file.rs::the_sp5_arm_files_are_the_committed_denial_perturbations` pins that, checks each value against the committed bounds, and fails on any `sp5*` file in the directory that nobody preregistered. The committed weights-arm count moves from 56 to 58 with these two files.

**Why the reference is the draft kind and not `base`.** The credit only exists inside the lookahead, so measuring it against the shipped greedy placement would bundle it with the `+1.65pp` M-59 already attributed to the lookahead and answer a question M-59 has answered. Against `draft` the contrast is the credit alone. The three specs share the same kind, the same hero weights except for one key, the same opponent weights, the same legality, the same deterministic tie-breaking and the same road rule, so the tie-break difference that M-59's entry says it could not separate from the lookahead is common to all three arms here and cancels out of every comparison in this run.

**Why the opponent path is pinned to the field's weights in every arm.** The spec string takes two paths so the hero's formula can move while the model the lookahead replays the rest of the field with stays fixed, and every arm in this phase pins the opponent path to `simulator/placement/default-weights.json`. Two reasons, and the second is the one that matters here. First, it keeps the opponent model correctly specified by construction, as M-59 ran it: the three rival seats really are running the formula the lookahead assumes. Second, `setupDenialWeight` is read only through the hero path, so an arm that also moved it on the opponent path would change what the replayed rivals themselves pick and the contrast would no longer be one term. Nothing in a JSON file can pin that half; the committed command below and this document are where it lives.

**What the arm moves, which is one pick at three of the four slots.** Only the hero's first settlement. The second settlement is `draft.rs::best_direct`, the plain formula argmax, and `AppFormulaScorer::score_for_owner` does not read `setupDenialWeight`; the setup road is `draft.rs::setup_road` at the hero weights, which does not read it either. So the credit reaches the argmax over first-pick candidates and nothing else. **At slot 3 it reaches nothing at all.** `Lookahead::new` sets `intervening` to `first + 1..last` over `setup_order`, and the seat that picks last in the first round picks twice in a row, so that range is empty, `denial` stays 0, and `value` returns the same `f64` it returns at weight 0, since adding a positive zero changes no finite value. The hero at slot 3 therefore plays a game that is identical to the reference's, pick for pick and draw for draw. That is a structural fact about the design and it has three consequences stated before the run: **a quarter of the paired units are concordant by construction**, the pooled estimate is diluted by that quarter whatever the effect at the other slots is, and slot 3's row of the per-hero-seat table must come back with `b` and `c` both exactly 0.

**The credit sums over positions, not over distinct rivals.** `replay` charges each intervening position, and at four seats the slot 0 window holds six of them, which is every rival twice. A rival that would have taken the hero's candidate at both its first and its second pick is charged for it twice. The window is six positions at slot 0, four at slot 1, two at slot 2 and none at slot 3, so **the same weight buys a systematically larger nudge the earlier the hero picks**, both because there are more positions to sum and because the early positions are the ones where a rival can still want the vertex. The credit is not normalized by the window, and this run measures the term as Task 23 built it rather than a normalized variant of it. The consequence for the reading is that a slot gradient in this run is not evidence about slot conditioning in the SP4 sense; it is the term's own shape.

**Why the credit is sparse, which sets the activity expectation.** For any candidate the hero is not considering as a denial, `denial_gain` is exactly 0, because vacating a vertex that is not the rival's argmax leaves the rival's best untouched and the two scans return the same number. So the credit is a bonus on a handful of vertices, at most one per intervening position, and zero on every other legal candidate. Those credited vertices are the intervening rivals' argmaxes under the shipped weights, which is the same weights file the hero scores with, so they overlap heavily with the hero's own strong candidates and the credit frequently reinforces a leader rather than displacing one. That is the mechanism M-59's entry says three predictions in a row got wrong from the other direction: activity is set by how often a term reorders the top of a candidate list, not by how large the term is.

**Why this field.** A placement change has to be scored against the live placement, so the field stays `app_formula:placement/default-weights.json` and `simulator/crates/cli/src/evaluate.rs` gives the arm to the hero seat alone, per the plan's protocol and following M-51 through M-54 and M-57 through M-59. Every seat runs the post-SP1 composite `heuristic-v1-trader-aware-threat-devcards-denial` with player trading. So the hero drafts with a lookahead and a denial credit against three seats that draft greedily and never deny anything. That asymmetry is the measurement, and it is worth naming what it excludes: a field where every seat denied would be a different question, and in particular the externality argument above assumes the two rivals who are not being denied are not themselves paying to deny.

**Design.** `evaluate`, `standard4`, 4 seats, `--domain tuning`, 2000 boards x 2 reps, which is 16,000 paired units over 2000 clusters, `--threads 0`, `--threshold 0.01`, `--alpha 0.05`, reference `draft`, all three specs in one invocation, 48,000 games. That is the plan's screen power for an optional term, matching M-38's placement screens, M-49, M-52, M-53, M-54's screen, M-57, M-58 and M-59.

**Power, and the dilution that is known before the run.** At this power the pooled rows of M-54 came back with half-widths of `+/-0.71pp` and `+/-0.78pp`, M-57's with `+/-0.35pp`, M-58's with `+/-0.47pp` and `+/-0.50pp` and M-59's with `+/-0.68pp`, the width tracking how many units each change made discordant. This term should be less discordant than any of them, so the interval should sit at the narrow end, near `+/-0.35pp` for `denial_lo` and nearer `+/-0.5pp` for `denial_hi`. The complication is not the width but the estimate: slot 3 contributes 16,000 divided by 4 units of guaranteed agreement, so a uniform effect `x` at the three slots that can move pools to `0.75x`. **The `+/-1pp` threshold is applied to the pooled estimate as the plan's standing rule requires and no dilution correction is applied to it**, because inventing a per-run correction after seeing which slots moved is exactly the discretion preregistration exists to remove. The dilution is instead declared here so the M entry reads the pooled row knowing it, and the per-hero-seat table from Task 1 is the reading of record for where the term acts, carrying no verdict of its own.

**Timing, preregistered before the run.** A 200-board calibration was run before this document was written, at `--threads 1` and carrying all three specs exactly as the command below carries them: 4,800 games in 10.82 seconds, or 443.6 games per second on a single worker, load `1.65 2.21 2.12` before and `1.55 2.17 2.10` after. **Only the elapsed time and the game count were read off that run; none of its estimates, verdicts or discordant counts were.** Every game in this screen carries a draft hero, against M-59 where half did, so the pessimistic floor of no parallel speedup at all puts 48,000 games at 108 seconds and the 192,000-game retry at 433 seconds. At the 18 workers M-59 saw, an all-draft run should land near 5,400 games per second, which is 9 seconds for the screen and 36 seconds for the retry. **Both are predicted well under the plan's eight-minute mark, so both run in the foreground.** One trigger is fixed now so the contingency is not decided after seeing the clock: **if the screen's observed elapsed time exceeds 120 seconds**, then the retry, which is four times the work, is predicted past eight minutes and is launched in the background with `&` and polled by a loop that prints the elapsed minute while the process lives, per the plan's long-run rule, with the artifact read afterwards. No invocation is piped through `tail` or `head` in any branch.

**Decision rule (fixed before the run).** `sp5_denial_lo` is an ordinary optional term under the plan's standing disposition rule, applied without discretion: `better` keeps 0.25 as a surviving SP6 candidate, `worse` drops it and the M entry records why it was expected to help, `equivalent` at this declared power drops it and records the null as the answer, and `inconclusive` buys units exactly once at four times the boards with `--reps` unchanged, in the retry invocation above, after which a second `inconclusive` records the term unresolved and stops. **`sp5_denial_hi` carries a preregistered null and is not an ordinary arm.** The expected reading is `equivalent` or `worse` against the `+/-1pp` threshold, on the externality argument above that 1.0 overprices a rival's loss by roughly a factor of three. `equivalent` at screen power **confirms** the null and is the outcome that makes the arm worth running: it says the overpriced end of the axis is not merely unhelpful but indistinguishable, which bounds the axis from above without a sweep. `worse` also confirms it, more strongly, and the M entry records the magnitude. `inconclusive` **confirms nothing** and buys the same single retry, in the same invocation, since a null that cannot be distinguished from a `+1pp` effect is not a null that has been observed. `better` **refutes** the null, and it is the reading that would matter most: it would say the hero captures more than a proportional share of what it denies, that the axis is not bracketed by these two values, and that a proper sweep of it belongs in SP6. In that branch 1.0 is recorded as a surviving SP6 candidate and flagged as an unbracketed one, and no larger value is tried in this run, because choosing a third arm after seeing two readings is choosing the arm from the data. The two arms are dispositioned independently; if both read `better` the better-reading value is the survivor and the other is recorded. Record only in every branch: no shipped default moves, in `src/engine/weights.ts`, `simulator/placement/default-weights.json`, `simulator/placement/phase-i-candidate-weights.json` or anywhere else, `setupDenialWeight` stays at 0 in every shipped vector, the two arm files stay the only committed files carrying a nonzero value, and the field's placement stays `app_formula:placement/default-weights.json`. No entry in `.claude/specs/simulator/gaps.md` moves on this reading in any branch. `SIM-GAP-20` closed on M-59 and is already gone; `SIM-GAP-34` does not move, because a term left at 0 closes nothing.

**Prediction (recorded before the run).** I predict **`denial_lo` reads slightly positive and short of the threshold**, with a pooled point estimate between `-0.1pp` and `+0.6pp`, most likely `inconclusive` and otherwise `equivalent`, on 400 to 1,400 discordant units of 16,000. I predict **`denial_hi` reads flat to negative**, with a pooled point estimate between `-1.2pp` and `+0.2pp`, most likely `inconclusive` or `equivalent` and with a real chance of `worse`, on 1,200 to 3,200 discordant units. Three arguments set those. The direction on `lo` is that 0.25 is just under the break-even share and the sparse credit mostly reinforces candidates the hero already leads with, so it should behave like a small, occasionally useful tiebreak toward contested vertices; the direction on `hi` is that 1.0 buys a rival's loss at three times what the hero collects from it, and the hero pays for it in the one currency the lookahead has already shown to be worth `+1.65pp`, its own pair value. The activity brackets are set low deliberately and against the shape of my last three predictions: the credit is exactly 0 on all but a handful of candidates per board, and those few are the rivals' argmaxes under the same weights file the hero scores with, so displacement requires the hero's leader and the rivals' target to be different vertices **and** to be within the credit of each other. The `hi` bracket is roughly triple the `lo` bracket because the credit scales linearly and the window of candidates it can flip scales with it.

Per slot, I predict **exactly zero at slot 3 on both arms, with `b` and `c` both 0**, which is a structural claim and not an estimate, and **magnitudes ordered slot 0 above slot 1 above slot 2** on both arms, following the six, four and two positions the credit sums over. I do not predict the sign to be the same at every slot. Three readings would change my mind and are named now so they cannot be explained away afterwards. **`denial_hi` reading `better`** would refute the externality argument outright and say a rival's loss is worth more to the hero than a proportional share, most likely because a setup denial compounds over the game in a way a one-pick score difference does not price; that is the branch that sends the axis to SP6 unbracketed. **A negative reading on `denial_lo` larger than a few tenths of a point** would say the credit is harmful at any price, which would most likely mean the sparse bonus is displacing the hero's leader with a vertex whose pair value is genuinely worse and that the lookahead's own valuation is better than a denial heuristic at every weight. **Slot 3 discordant on either arm** would mean the structural claim above is wrong, which would make the run inadmissible rather than informative, and it is registered as an admissibility check below rather than as a finding.

**Threshold and alpha.** `+/-1pp` practical threshold, alpha 0.05. Interval selection is the harness's own rule in `evaluate.rs::try_paired_stats`, the wider of the McNemar and board-clustered intervals.

**Admissibility.** The release binary is built before the measurement starts and the build is confirmed to report `Finished` against a warm fingerprint, which is M-50's lesson and the plan's explicit rule that a build must not land inside the timed window. `uptime` is recorded immediately before and immediately after each `evaluate` invocation and every reading enters the M entry, along with the games per second. No invocation shares its command block with a build, a test suite or any other CPU-heavy job. Zero illegal actions required. Timing is a throughput observation only; the outcomes are deterministic in the seeds and unaffected by load. Three checks are registered now and a failure of any one of them makes the run inadmissible.

- **The reference reproduces M-59's `draft` arm to the game.** M-59 ran this exact spec on this exact domain seed at this exact power and recorded 4,249 wins of 16,000 on its screen and 16,967 of 64,000 on its retry. The only placement code that has moved since is `setupDenialWeight`, which the reference carries at 0 and which Task 23 pinned as forming no credit at all at that value. A mismatch would mean the credit reached a path it was pinned out of.
- **Slot 3 is exactly concordant on both arms**, `b` and `c` both 0 in the per-hero-seat rows, for the structural reason set out above. A nonzero count would mean the credit is reaching a slot whose intervening window is empty.
- **Per-seat `n` sums to the pooled `n` and per-seat `b + c` sums to the pooled `b + c`** on every arm, which is the invariant Task 1's CLI test asserts and which the M entry restates from the artifact.
