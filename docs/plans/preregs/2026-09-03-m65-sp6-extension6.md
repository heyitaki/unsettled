# M-65 preregistration: the SP6 candidate on `extension6` at six seats

Date: 2026-09-03. Committed before the run.

**Standing of this run: record only, and it cannot block adoption.** The `## SP6 decisions, 2026-09-02` note in `.claude/specs/simulator/placement-programme.md` fixes one record-only extension reading: the final package is read once on `extension6` at 6 seats on `tuning2`, it cannot block adoption, and a `worse` reading is flagged for the user. This is that reading. It runs before the gate so its result is in the record whatever `gate2` reads, and no branch of it changes what Tasks 15 through 17 of `docs/plans/simulator-placement-sp6.md` do. `tuning2` is SP6's screening domain and screens freely, so this run spends nothing; `eval2` is already spent by M-64 and `gate2` is untouched here.

**Condition, and why it did not fire.** Tasks 13 and 14 are conditional on M-63. The condition they name is Task 9's no-survivor skip, which would have ended SP6 at the re-screen. It did not fire: M-62 left exactly one survivor, `(expansionWeight, 0.1)`, so Task 9 took its one-survivor branch, M-63 recorded the coordinate pass as not needed, and M-64 then confirmed the candidate on `eval2` at `+0.934pp` `better`. This preregistration is therefore written and the run executes.

**Change under test.** One arm, the SP6 candidate vector, against the field's own weights, the same single contrast M-64 confirmed and the same one M-66 will decide. The candidate is `simulator/placement/sp6-candidate-weights.json`, the live `simulator/placement/default-weights.json` with `expansionWeight` moved from 0 to 0.1 and nothing else moved: `expansionDecay` stays at 0.5, `robberConcentrationWeight` at 0, `diversityWeight` at 1.6. `simulator/crates/engine/src/policy/params_file.rs::the_sp6_candidate_file_records_the_combined_vector` walks every leaf of the shipped vector and pins that the moved set is exactly that one axis at that value, checks it against `simulator/placement/sweep-bounds.json`, and pins the file equal to `simulator/placement/arms/sp6_expansion.json`, so the vector read here is the vector M-62 screened and M-64 confirmed.

**What this run asks.** Every SP6 reading so far has been taken on `standard4` at four seats, and each of those entries records in terms that it does not transfer to `extension6` or to 3, 5 and 6 seat games. This run is the one observation of the candidate outside that corner. The question it asks is whether the expansion term's sign survives a bigger board and a longer draft, not what its size is there: the power available at this layout will not resolve a 0.5pp effect, and the design says so below rather than discovering it afterwards.

**Two structural differences the reading has to carry, and they push in opposite directions.** First, the fill at the end of setup is almost identical, so the boxing pressure the expansion term prices is not obviously different: `simulator/topology/extension6.json` has 80 vertices and takes 12 setup settlements, a fill of 0.150, against `simulator/topology/standard4.json` at 54 vertices and 8 settlements, a fill of 0.148. Second, the draft is longer, and that bears directly on the misspecified opponent model. `simulator/crates/engine/src/game.rs::setup_order` runs `0..seats` then reversed, so at six seats slot 0 has **10 intervening picks** between its two settlements against 6 at four seats, and the lookahead in `simulator/crates/engine/src/placement/draft.rs` must replay all of them greedily. M-61 measured that greedy model at 39.4% of intervening picks named exactly and 23.6% of first picks reaching the board the game actually reached, both at four seats; a window half again as long compounds the same per-pick error over more picks, so the lookahead's plan should be a worse description of the board the hero actually returns to. The honest prior is that a longer window costs the draft-aware hero some of its edge and the expansion term some of its credit, and that a larger board with more room to expand returns some of it.

**Design.** `evaluate`, **`extension6`, 6 seats**, `--domain tuning2`, field `app_formula_draft:placement/default-weights.json@placement/default-weights.json`, every seat on `heuristic-v1-trader-aware-threat-devcards-denial` with `--player-trading`, `--threads 0`, **2000 boards x 2 reps**, **`--threshold 0.005`**, `--alpha 0.05`, run from `simulator/`. `simulator/crates/cli/src/evaluate.rs::evaluation_schedule` crosses boards, reps and hero seats, so six seats give 12 units per board against four seats' 8: this is **24,000 paired units over 2,000 clusters**, and 48,000 games over the two arms. Six seats is an official combination for this layout in `evaluate.rs::validate_request`, so no `--allow-unofficial` is needed. Reference `base` carries the field spec itself and sits at the symmetric **1/6 corner**, not the 0.25 corner every four-seat SP6 entry checked. The decision arm carries the candidate on the hero path with the opponent path pinned to the field's weights, per the draft-aware arm contract in `.claude/specs/simulator/contracts.md`, so the arm moves the hero's formula and nothing about the opponent model.

**Commands.** Build first, from the repo root, so no compile lands inside a timed window:

```text
RUSTFLAGS="-D warnings" cargo build --release --manifest-path simulator/Cargo.toml -p unsettled-sim
```

Then the single invocation, from `simulator/`, with `uptime` recorded immediately before and immediately after:

```text
target/release/unsettled-sim evaluate --layout extension6 --seats 6 --domain tuning2 --field app_formula_draft:placement/default-weights.json@placement/default-weights.json --arm base=app_formula_draft:placement/default-weights.json@placement/default-weights.json --arm candidate=app_formula_draft:placement/sp6-candidate-weights.json@placement/default-weights.json --reference base --boards 2000 --reps 2 --policy heuristic-v1-trader-aware-threat-devcards-denial --threads 0 --player-trading --threshold 0.005 --alpha 0.05 --out runs/m65-sp6-extension6
```

The two weights files carry distinct stems, `default-weights` and `sp6-candidate-weights`, which is what keeps `simulator/crates/cli/src/heuristics.rs::parse_heuristic` from rejecting the pair on a label collision. The invocation is not piped through `tail` or `head` and does not share its command block with the build, a test suite or any other CPU-heavy job.

**Timing, measured rather than extrapolated from another layout.** `extension6` is a new layout for SP6, so the plan's pilot rule fires and the pilot has already been run, before this preregistration was written. Load before `3.01 4.52 5.21`, after `5.48 5.00 5.37`; 200 boards x 2 reps x 6 seats x 2 arms, **4,800 games in 5.477s at 18 workers**, 876.4 games/s, zero illegal actions, domain `tuning2` at seed 8796197394747623682. That is 1.141e-3s per game against the 4.65e-4s per game M-64 measured on four-seat `standard4`, so a six-seat extension game costs about 2.45 times a four-seat standard one. The full run is exactly ten times the pilot's schedule, 48,000 games, so it extrapolates to about **55 seconds**. That is far under the eight-minute bar, so **it runs in the foreground and no background-and-poll invocation is registered.**

**The pilot's paired statistics were not read, deliberately.** `evaluate.rs::evaluate` generates board `i` from `mix64(domain_seed ^ i)`, so the pilot's 200 boards are exactly boards 0 through 199 of this run's 2000 and its units are a strict 10% subset of the units this run will pool. Reading its estimate would be a peek at the outcome before the prediction below was written. Only `meta.json` was opened, for the two timing figures quoted above; `runs/m65-pilot-200/evaluation.json` was left unread and `simulator/runs/` is gitignored, so nothing from either the pilot or the run enters the tree.

**Decision rule (fixed before the run), and what "record only" means concretely.** There is no decision. No verdict from this run adopts anything, rejects anything, changes the candidate vector, or changes whether M-66 runs on `gate2`. `better`, `equivalent` and `inconclusive` are all recorded in the M entry and nothing follows from them. **On `worse`, the whole selected interval below `-0.005`, the reading is flagged for the user**: the M-65 entry opens with the flag, Task 18's SP6 completion note carries it, and the run summary names it, so that a decision to adopt on `gate2` is taken with the extension result visible rather than buried. Even then it does not block: the gate rule the user fixed on 2026-09-02 is `gate2` alone, and this entry is evidence for a future phase to act on, not a veto. There is no retry at any outcome and no second invocation.

**Power, and the fact that `equivalent` is out of reach here.** This is the design's chief limitation and it is stated in advance so no reading is over-claimed afterwards. The 2000 x 2 size is fixed by Task 13 of the plan, which is a quarter of M-64's cluster count: 2,000 clusters against 8,000. The clustered interval `simulator/crates/cli/src/evaluate.rs::try_paired_stats` selects is driven by cluster count, so a quarter of the clusters is roughly twice the half-width, and each cluster here carries 12 correlated units rather than 8, which does not help. M-64 delivered `+/-0.3555pp` on the same contrast, so I expect **`+/-0.7pp` to `+/-0.9pp`** here. Three consequences follow. A `better` verdict needs a point estimate above about `+1.2pp`, which is well above anything this contrast has read on four seats. A `worse` verdict, the flag condition, needs an estimate below about `-1.2pp`. And **`equivalent` is structurally unreachable**, because it requires the whole interval inside `+/-0.5pp`, which needs a half-width under 0.5pp that this cluster count cannot deliver: an `equivalent` reading here would mean the interval came in far tighter than predicted and would itself be the surprise. **`inconclusive` is therefore the modal outcome by construction, and an `inconclusive` reading is not a null.** The run is sized to see a sign and a rough magnitude on a corner nothing else in SP6 observes, not to resolve the 0.5pp bar there.

**Prediction (recorded before the run).** I predict a point estimate **between `0pp` and `+1.0pp`, centred near `+0.6pp`**, and I predict **`inconclusive`** as the verdict, at odds I would put near four in five, with `better` the main alternative and `worse` a real surprise. Two arguments set that centre. The win-rate corner is 1/6 rather than 1/4, so there is a third less win probability available to redistribute and a term worth `+0.934pp` at four seats scales to roughly `+0.62pp` on that argument alone. Against it, the longer intervening window should cost the draft-aware hero accuracy at every slot, which shrinks the expansion term's credit further, while the larger board leaves more room for an opened fan to be worth something, which returns some. I expect those two to roughly cancel and the corner-scaling argument to dominate. On slot structure I predict the same mild slope M-62 and M-64 both found rather than M-54's slot-0 spike, with the early slots above the late ones and slot 5 lowest, because slot 5 picks twice in a row with no intervening window at all and so gets the least from a lookahead; that is a record-only prediction on six slot rows each carrying 4,000 units, where the per-slot half-width will be roughly twice the pooled row's and almost nothing will separate.

**Admissibility.** The release binary is built with `RUSTFLAGS="-D warnings"` in its own command block before the measurement starts and must report `Finished` against a warm fingerprint, which is M-50's lesson. `uptime` is recorded immediately before and immediately after the invocation and both readings enter the M entry. **Zero illegal actions required**, or the run is inadmissible. The invocation must report domain `tuning2` at seed 8796197394747623682, the decimal form of `0x7a12_5eed_2026_0902`; a run naming `tuning`, `eval` or `gate` is inadmissible on its face because all three are spent, one naming `eval2` is inadmissible because M-64 spent it, and one naming `gate2` is inadmissible because the gate is M-66's single spend. `base`'s win rate is checked against the symmetric **1/6** corner, and because `base` carries the field spec exactly this is also the drift check. **`base` must not be compared with M-62's or M-64's reference win rate**, because the layout, the seat count and the board schedule all moved; this run establishes the first six-seat draft-aware `base` win rate on `extension6` and nothing here reproduces a four-seat figure.

**Threshold and alpha.** `+/-0.5pp` practical threshold, passed as `--threshold 0.005` because the flag takes a fraction, per SP6's standing threshold in `.claude/specs/simulator/contracts.md`. Alpha 0.05. Interval selection is the harness's own rule in `evaluate.rs::try_paired_stats`, the wider of the McNemar and board-clustered intervals.

**Scope, and what the entry may not be cited for.** One contrast, one axis, one layout, one seat count, one policy, one domain. The arm moves the hero's weights alone against five seats carrying the field's, so nothing here measures a field where every seat carries `expansionWeight` 0.1. The arm moves the setup road as well as the settlement, because `draft.rs::setup_road` applies SP3's road rule and falls through to far-endpoint scoring only at `expansionWeight` 0, so this reading bundles the two effects exactly as M-62's and M-64's did. The reading is taken against the greedy opponent model M-61 measured at four seats and never measured at six, so **no verdict here may be described as taken against a correctly specified model**, and the misspecification is expected to be worse here than anywhere else in SP6 for the window-length reason given above; what keeps it from biasing the contrast is that the arm and the reference carry the same opponent weights file on the same greedy replay. Nothing here transfers back to `standard4`, to 3, 4 and 5 seat games, or to `extension6` at five seats, which this run does not observe. The per-hero-seat table is record-only and carries no verdict.

**No shipped default moves.** Not `src/engine/weights.ts::DEFAULT_WEIGHTS`, not `simulator/placement/default-weights.json`, not `simulator/placement/sp6-candidate-weights.json`, not any params file. `SIM-GAP-34` stays open in `.claude/specs/simulator/gaps.md` whatever this run reads, because that gap closes on adoption and adoption sits behind M-66. Beyond the M entry, the task that records this run changes no document: `tuning2` is a screening domain with no ledger entry to update.

**Numbering.** M-64 is the last entry in `.claude/specs/simulator/measurements.md` at this commit, so this run takes M-65. If that file has moved on by the time the run executes, the entry takes the next unused number and this preregistration is cited by filename.
